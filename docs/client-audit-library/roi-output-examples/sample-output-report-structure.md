# Структура выходного отчёта после аудита

Этот шаблон описывает, какой пакет решений клиент получает после аудита возможностей искусственного интеллекта. Его можно использовать как основу для коммерческого предложения, финального отчёта или демонстрационного примера на сайте.

## 1. Управленческое резюме

Цель раздела — дать руководству ответ на три вопроса:

1. Где в компании есть измеримый потенциал улучшений?
2. Что нужно делать первым?
3. Какие пилоты имеют понятную экономику и приемлемый риск?

Содержание:

- краткое описание обследованных процессов;
- 3-5 главных выводов;
- список приоритетных сценариев;
- оценка окупаемости по диапазонам;
- решения, которые не требуют искусственного интеллекта;
- решения, где искусственный интеллект может дать дополнительный эффект;
- ключевые риски и ограничения.

## 2. Границы аудита

Содержание:

- подразделения и процессы, которые вошли в аудит;
- роли, с которыми проведены интервью;
- список полученных данных и документов;
- ограничения анализа;
- что не входило в аудит.

Пример формулировки:

> Анализ основан на интервью, примерах документов, выгрузках операций и управленческих отчётах, предоставленных компанией. Расчёты являются предварительной оценкой и требуют уточнения перед запуском пилота.

## 3. Карта процессов

Для каждого выбранного процесса:

- начало процесса;
- участники;
- системы;
- ручные операции;
- точки передачи ответственности;
- статусы;
- документы и данные;
- узкие места;
- места, где возможна автоматизация или поддержка искусственным интеллектом.

Формат:

| Этап              | Участник              | Система                  | Ручная работа       | Проблема                 | Возможность улучшения             |
| ----------------- | --------------------- | ------------------------ | ------------------- | ------------------------ | --------------------------------- |
| Получение данных  | Закупщик              | Таблица, учётная система | Выгрузка и сведение | Данные опаздывают        | Автоматическая витрина            |
| Анализ исключений | Категорийный менеджер | Таблица                  | Ручной поиск причин | Решения зависят от опыта | Подсказки и объяснение отклонений |

## 4. Реестр узких мест

Каждое узкое место описывается как проверяемая гипотеза.

| Узкое место                        | Последствие для бизнеса     | Как проверить                     | Метрика           | Приоритет |
| ---------------------------------- | --------------------------- | --------------------------------- | ----------------- | --------- |
| Остатки расходятся между системами | Ошибки пополнения и дефицит | Сравнить остатки по источникам    | Доля расхождений  | Высокий   |
| Документы классифицируются вручную | Задержка старта проекта     | Измерить время первичного разбора | Минут на документ | Средний   |

## 5. Расчёт окупаемости

Раздел содержит:

- исходные данные;
- допущения;
- формулы;
- консервативный, базовый и высокий сценарии;
- стоимость запуска;
- стоимость владения;
- период окупаемости;
- чувствительность к ключевым параметрам.

Формат итоговой таблицы:

| Сценарий       | Валовый эффект в год | Стоимость владения в год | Чистый эффект первого года | Период окупаемости |
| -------------- | -------------------: | -----------------------: | -------------------------: | -----------------: |
| Консервативный |                      |                          |                            |                    |
| Базовый        |                      |                          |                            |                    |
| Высокий        |                      |                          |                            |                    |

Обязательная пометка:

> Расчёт показывает потенциал при указанных допущениях. Перед запуском пилота требуется проверка на фактических данных, уточнение стоимости запуска и согласование критериев качества.

## 6. Разделение решений по типу

Не все улучшения должны быть связаны с искусственным интеллектом.

### Сначала данные, процесс и обычная автоматизация

Примеры:

- единые справочники;
- обязательные статусы;
- контроль полноты данных;
- интеграция между системами;
- отчётность по ключевым метрикам;
- шаблоны документов;
- правила маршрутизации;
- база знаний.

### Затем сценарии с искусственным интеллектом

Примеры:

- извлечение данных из документов;
- классификация обращений;
- поиск по внутренней базе знаний;
- прогноз спроса;
- выявление аномалий;
- рекомендации сотруднику;
- подготовка черновика ответа или отчёта.

## 7. Приоритизация сценариев

Матрица оценки:

| Сценарий                            | Потенциальный эффект | Сложность запуска | Готовность данных |    Риск | Рекомендация               |
| ----------------------------------- | -------------------: | ----------------: | ----------------: | ------: | -------------------------- |
| Прогноз дефицита по категориям      |              Высокий |           Средняя |           Средняя | Средний | Пилот после очистки данных |
| Извлечение реквизитов из документов |              Средний |            Низкая |           Высокая | Средний | Узкий пилот                |
| Полная автоматизация закупки        |              Высокий |           Высокая |            Низкая | Высокий | Не запускать первым        |

## 8. Дорожная карта на 90 дней

Пример структуры:

### Дни 1-15: подготовка

- назначить владельца процесса;
- согласовать метрики;
- собрать данные;
- описать правила качества;
- определить ограничения доступа.

### Дни 16-45: пилот

- настроить ограниченный сценарий;
- подключить тестовые данные;
- организовать проверку человеком;
- сравнить результат с текущим процессом;
- фиксировать ошибки и исключения.

### Дни 46-75: оценка

- посчитать фактическое время;
- сравнить качество;
- уточнить стоимость владения;
- оценить готовность пользователей;
- решить, нужен ли следующий цикл.

### Дни 76-90: решение о масштабировании

- подготовить бизнес-обоснование;
- согласовать архитектуру;
- определить бюджет;
- принять решение: остановить, доработать или масштабировать.

## 9. Реестр рисков

| Риск                           | Почему важен                              | Как снизить                                          |
| ------------------------------ | ----------------------------------------- | ---------------------------------------------------- |
| Низкое качество данных         | Расчёт и рекомендации будут искажены      | Проверка источников, очистка, владельцы справочников |
| Нет владельца процесса         | Пилот останется техническим экспериментом | Назначить бизнес-владельца до запуска                |
| Ошибки результата критичны     | Нельзя доверять автоматике решение        | Обязательная проверка человеком                      |
| Скрытая стоимость поддержки    | Окупаемость будет завышена                | Считать стоимость владения отдельно                  |
| Пользователи не меняют процесс | Эффект не реализуется                     | Обучение, регламент, контроль использования          |

## 10. Архитектурные рекомендации

Раздел готовится вместе с ИТ-директором или ответственным за системы.

Содержание:

- какие системы являются источниками данных;
- где должна храниться рабочая витрина;
- какие данные можно обрабатывать в облаке, а какие нельзя;
- какие интеграции нужны для пилота;
- как ограничиваются права доступа;
- как логируется работа решения;
- кто отвечает за качество данных и результата.

## 11. Пакет документов на выходе

Минимальный пакет:

1. Карта процессов.
2. Реестр узких мест.
3. Реестр сценариев улучшения.
4. Расчёт окупаемости по 3-5 сценариям.
5. Матрица приоритизации.
6. Дорожная карта на 90 дней.
7. Архитектурные рекомендации.
8. Реестр рисков.
9. Запрос данных для следующего этапа.
10. Решение по пилоту: запускать, уточнять или отложить.

## 12. Формат финального решения

Для каждого сценария в конце отчёта фиксируется один из статусов:

- **Запускать пилот** — есть владелец, данные, экономика и приемлемый риск.
- **Уточнить данные** — идея перспективна, но расчёт пока слабый.
- **Сначала исправить процесс** — без данных, статусов или регламента искусственный интеллект преждевременен.
- **Отложить** — эффект мал, риск высок или стоимость запуска не соответствует масштабу.

Такой формат помогает руководству принять решение, а не просто получить презентацию.
